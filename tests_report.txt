LoraCore Emulation Audit Report
===============================

Scope:
- VirtualCpu instruction set (ALU, branches, stack).
- SystemBus address mapping and access pattern.
- VirtualMachine task queue and consumeCycles grace period.
- JarClassLoader usage and potential memory leaks.

1) VirtualCpu Instruction Set "Brain Test"
-----------------------------------------

ALU operations:
- ADD, SUB, MUL, DIV, MOD operate on 32-bit int registers with in-place update of the destination register and call updateFlags(result).
- ADDI and SUBI correctly use the signed 16-bit immediate (simm16), so negative immediates work as expected.
- DIV and MOD guard against division by zero by incrementing errorCount instead of throwing, so the VM is fault-tolerant here.

Logic operations:
- AND, OR, XOR, NOT correctly operate on full 32-bit registers and update flags.
- ANDI/ORI use the 16-bit immediate as an unsigned mask, which is acceptable for typical bitmasking use-cases.
- SHL/SHR use (imm16 & 0x1F) as shift count, clamping to 0–31 and avoiding undefined behavior.

Jumps and comparisons:
- CMP and CMPI compute (Rdest - Rsrc/simm16) and feed the result into updateFlags.
- JZ and JNZ check FLAG_ZERO, JG checks (not ZERO and not NEGATIVE), JL checks NEGATIVE. This matches the standard "signed comparison via result flags" pattern.
- JMP, CALL and RET use the 16-bit immediate as an absolute byte address, not an instruction index. PC is incremented before decode, so the immediate is the next PC value, which is consistent once the assembler is aware of it.
- CALL pushes the return address (already incremented PC) to the stack and RET restores it. Stack pointer is initialized to 0x0FFC, so in the default 4 KB RAM window this leaves space for the stack.

Stack and memory safety:
- PUSH decrements SP by 4 and writes a full int at [SP].
- POP reads from [SP] and then increments SP by 4, so pairs of PUSH/POP restore the stack pointer exactly.
- The actual memory accesses go through SystemBus.writeInt/readInt, which perform strict bounds checking and throw HardwareInterruptException if out of range. This is a deliberate "hardware fault" rather than silent memory corruption.

Unimplemented opcodes:
- InstructionSet defines several opcodes (IN, OUT, INT, CPUID) that are not implemented in VirtualCpu.step and fall into the default branch.
- Default branch logs a "CPU FAULT" warning and increments errorCount but does not halt the CPU. This is acceptable for now but should be documented as "undefined / reserved".

Conclusion:
- ALU, jumps and stack behavior are internally consistent.
- There is no obvious arithmetic or flag logic bug for the supported opcode subset.
- Undefined opcodes are handled in a fail-soft way via errorCount.

2) SystemBus Logic and Safety
-----------------------------

Address mapping:
- Devices are mapped via mapDevice(startAddress, device) with full range checks against the global 16 MB space.
- Overlaps between devices are detected using an array of MappedDevice descriptors; any overlap throws an IllegalStateException at mapping time.

Segmented access:
- The bus divides the address space into 256 segments of 64 KB each. For each segment it keeps a small fixed-size array of IMemoryMappedDevice references plus a deviceCount per segment.
- readByte/writeByte/readInt/writeInt compute the segment index as address >>> 16, then scan only devices that are present in that segment.
- For each such device they locate the corresponding MappedDevice descriptor and check whether the requested address lies inside its [baseAddress, endAddress] range.

Bounds and fault behavior:
- All public read/write methods fully validate that the address lies inside the global [0, MAX_ADDRESS] range and throw HardwareInterruptException otherwise.
- readInt/writeInt also check that a 4-byte access does not cross the global upper bound; if a multi-byte access crosses a device boundary, they transparently fall back to repeated byte accesses via readByte/writeByte.

Performance considerations:
- The inner loops are simple indexed for-loops over small arrays; there is no allocation in the hot path.
- The nested loop over segment devices and allDevices is O(N^2) in the worst case, but with the current limits (<=64 devices total, default 4 devices per segment) this is acceptable for a Minecraft mod.

Conclusion:
- SystemBus is memory-safe with respect to address bounds.
- Device overlap is prevented at mapping time.
- No obvious race or aliasing issues are present because all access is synchronous on the server thread.

3) VirtualMachine Task Queue and Grace Period
---------------------------------------------

Task queue concurrency:
- taskQueue is a java.util.LinkedList<Runnable>.
- enqueueTask is synchronized and only enqueues when the VM is powered on.
- tick() processes the queue via a while loop that calls consumeCycles(100) for each task and then polls from taskQueue without explicit synchronization.
- All enqueueTask calls in ModNetworking are scheduled with server.execute(...), which runs on the main server thread, and tick() is also invoked from the same thread (END_SERVER_TICK).
- Under this threading model, there is no real concurrent access to taskQueue, so the absence of a synchronized block around the polling loop is safe in practice.

Grace period behavior:
- start() initializes cycleBudget to a small bootstrap value and sets bootGracePeriodEnd = now + 15000 ms.
- consumeCycles(cycles) first checks the real-time grace window; if now < bootGracePeriodEnd, it increments cyclesConsumedInPeriod and returns true without touching cycleBudget.
- This means that all VFS and device tasks are allowed to run even if cycleBudget is currently exhausted, as long as the real-time grace period has not expired.
- After 15 seconds, consumeCycles enforces the cycleBudget as normal, which keeps the machine from over-consuming CPU forever.

Conclusion:
- Given the single-threaded usage pattern, there are no observable race conditions in taskQueue handling.
- The 15-second grace period correctly prevents "boot lockout" caused by empty instruction budgets during BIOS/VFS-heavy startup, while still feeding cyclesConsumedInPeriod into CPU load metrics.

4) JarClassLoader and Memory Leaks
----------------------------------

Server-side loader (com.loracore.computer.kernel.JarClassLoader):
- Extends URLClassLoader and implements a parent-last strategy for non-API packages, with parent-first delegation for API packages and logging.
- Instances are created in KernelManager.boot for each kernel .jar, using a temporary file on disk as the classpath URL.
- The temporary file is deleted in a finally block after boot.
- The class loader itself is not explicitly closed, but there is typically one loader per running kernel. It is eligible for GC once the associated TabletScreen and JavaRuntime are closed.

Kernel-side loader (com.lora.tabletos.core.JarClassLoader):
- Extends URLClassLoader with an empty URL array and a ConcurrentHashMap-based class cache.
- defineClassFromData(name, bytes) stores each defined class in the cache and returns the same Class instance for repeated calls.
- There is no mechanism to unload classes, but this is expected for JVM class loaders; the cache is bounded by the number of classes in a given app jar.

Leak assessment:
- There is no unbounded growth structure that persists across many app or kernel lifetimes. Each app/kernel yields one class loader and a finite set of classes.
- The only realistic leak scenario is repeated boot/unload cycles where references to old loaders are accidentally kept; current code does not store JarClassLoader instances globally, so this risk is low.

5) Overall Safety and Bottlenecks
---------------------------------

Safe aspects:
- CPU ALU, branching, and stack instructions are internally consistent and guarded by SystemBus bounds checks.
- SystemBus prevents device overlap and out-of-range accesses, converting them into HardwareInterruptException rather than silent corruption.
- Task queue usage is effectively single-threaded and guarded by a real-time grace period to avoid boot lockouts.
- JarClassLoader usage is localized; temporary files are cleaned up, and loaders are not stored in global registries.

Potential bottlenecks:
- SystemBus read/write operations perform nested loops over segment devices and allDevices; with many devices this may become a hot spot, although current limits keep it acceptable.
- Logging in VirtualCpu (DUMP, fault messages, bit-flip warnings) can produce a lot of log output under heavy load or unstable configurations.

Recommended future improvements:
- Consider explicit closing of URLClassLoader instances in KernelManager when kernels are shut down, to release native resources earlier.
- If the device count grows, SystemBus could precompute per-segment MappedDevice arrays to avoid scanning allDevices inside hot read/write loops.
